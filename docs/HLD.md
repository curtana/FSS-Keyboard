- 문서: HLD, 버전 **0.80** (2026-11-14)
- 상태: 초안. LLD 0.1이 올린 설계 변경 요청 DCR-01~21(오너 승인 2026-10-27)을 반영했다.

**의존 방향:** `app` → `stroke-core`, `core-hangul`, `recognizer`. `recognizer`는 `core-hangul`의 **자모 정의와 이벤트 형식**, 그리고 **천지인 조립(`CheonjiinAssembler`)**만 참조한다(조립기는 이슈 #160로 core-hangul에 둠). 조립기 객체(상태)는 앱의 그래피티 입력 처리부가 가진다. 조합 상태는 앱이 가진 조합기 하나에 있고, 엔진이 필요한 상태는 호출할 때 매개변수로 받는다. 0.78까지 있던 `gesture-engine`(`stroke-core`에 의존하던 긋기 자판 판정 모듈)은 긋기 입력 모드와 함께 없앴다(FSS#95).

## 4. 방향 긋기 판정과 한글 조합

0.78까지 이 장은 긋기 입력 모드의 처리 흐름이었다. 긋기 입력 모드를 지우면서(FSS#95) 탭 자판·모드 키가 쓰는 변 통과 판정(4.2)과 한글 조합기(4.4)만 남긴다. 절 번호는 그대로 둔다.

### 4.1 입력 뷰 공통 규칙 (0.78까지의 "긋기 자판의 한 획 흐름"은 삭제, FSS#95)

탭 자판의 터치 흐름은 5A, 그래피티는 5장이다. 모든 입력 뷰에 공통인 규칙 하나만 여기 남긴다.

- **ACTION_CANCEL**(플랫폼이 터치를 취소): 진행 중인 획을 결과 없이 버린다. 기능키 반복은 멈춘다(SRS FR-CMN-11a, DCR-11). 모든 입력 뷰(탭 자판, 그래피티 패드)에 같다.

### 4.2 변 통과 판정 (stroke-core)

**쓰는 곳:** 탭 자판의 글자·숫자·기호 키(`TapGestureClassifier`, 5A)와 모든 자판의 모드 키(`ModeKeyGesture`, 8.2). 둘 다 같은 `EdgeCrossingTracker`를 쓴다(SRS 3.4, FR-SWP-01~05·45). 0.78까지는 긋기 자판의 숫자·기호·천지인 키도 썼다.

- **처음 누른 키로만:** 획은 처음 누른 키의 사각형으로만 판정한다. 손가락이 다른 키 위나 자판 밖으로 나가도 그 키가 끝까지 받는다(SRS FR-SWP-01, AS-2). 키 안의 누른 위치는 쓰지 않는다(FR-SWP-02).
- **변 통과 기록:** 나감·들어옴을 변 너머(들어옴은 변 안쪽) `minCrossDp`(최소 통과 거리, 7.2) 이상 갔을 때 한 번으로 기록한다. 대각선은 먼저 통과한 변이다(FR-SWP-03·04). 기록이 없으면 탭이다(FR-SWP-05). 같은 변의 통과 횟수로 나갔다 돌아옴(2번)과 문지르기(3번 이상)를 가른다(SRS 1.3).
- **입력기 테두리에 닿은 변**(`KeyGeom.outerEdges`, 창 테두리에서 `OUTER_TOLERANCE_DP` 0.5dp 안의 변)은 획이 테두리(± 같은 허용 오차)에 닿으면 그 방향 나감으로 센다 — 그 방향으로 누른 점에서 `minCrossDp` 이상 움직였을 때만, 변 너머 `minCrossDp`에 먼저 닿으면 그때(오너 지시 2026-11-02, 이슈 #237, SRS FR-SWP-45). 0.54까지는 바깥 변을 기록하지 않았다. **왼쪽·오른쪽 테두리(SRS FR-CMN-14 ⑧, FSS#84):** 테두리의 왼쪽·오른쪽은 모드 뷰의 끝이 아니라 **자판 사각형의 바깥 변**(여유 칸의 바깥 변, 5A)이다. 그래서 왼쪽·오른쪽 끝 키의 바깥쪽 변은 `outerEdges`에 들지 않고 다른 변처럼 변 너머 `minCrossDp`에서 나감으로 센다. 테두리에 붙은 변(`KeyGeom.windowEdges`)으로 남는 것은 맨 아랫줄의 아랫변(`outerEdges`)과 맨 윗줄의 윗변(`topAtWindow`)뿐이다. 0.74까지는 끝 키의 바깥쪽 변이 테두리 변이었다.
- **결과 해석:** 탭 자판은 탭 자판 동작 표(SRS 3.3. ↑ = 시프트, FR-SWP-44)대로다(5A). 모드 키는 처음 통과한 변만 본다(8.2).
- 누른 시간은 결과를 바꾸지 않는다.

### 4.3 ~~SwipeInputMapper: 탭·획 → 자모~~ — 삭제 (FSS#95)

긋기 자판의 탭·모음 획을 자모로 바꾸던 부분과 모음 획 조립기(`VowelStrokeAssembler`)는 긋기 입력 모드와 함께 없앴다. 천지인 조립(`CheonjiinAssembler`, core-hangul)은 그래피티가 쓰므로 남는다(5장).

### 4.4 HangulComposer (core-hangul)

입력: `JamoEvent`. 출력: `ComposeResult(committed, composing)`. 생성할 때 **모드 정책**을 받는다.

| 정책 | 두벌식 | 그래피티 |
|---|---|---|
| 모음 병합 표 | 두벌식 표준(FR-HGL-04a) | 쓰지 않음(천지인 조립 결과를 `ReplaceVowel`로 받음) |
| 백스페이스 | 마지막 입력 단위(키 하나) 되돌림 | 마지막 입력 단위(자모 하나 또는 천지인 요소 하나) 되돌림 |

**입력 단위 목록:** 조합 중인 글자마다 그 글자를 만든 이벤트를 차례로 쌓는다. 백스페이스는 목록 끝에서 하나를 빼고 나머지로 상태를 다시 만든다(닭 ⌫⌫⌫ = 달, 다, ㄷ). 글자가 확정되면 그 글자의 목록은 버린다. 그래서 **백스페이스는 확정 경계를 넘지 않는다**(가가 ⌫ = 가ㄱ, 앞 가를 다시 열지 않음). 오류 복구(9장)도 같은 목록을 쓴다.

조합기는 확정된 글자를 보관하지 않고 확정 경계를 넘어 되돌리지 않는다.

```
상태: Empty → Cho → ChoJung → ChoJungJong(받침 1) → ChoJungJongJong(겹받침)
 · 모음 입력 시 받침이 있으면 받침(겹받침이면 뒤 자음)을 떼어 새 글자 초성(도깨비불)
 · 겹받침 자모 한 번에(SRS FR-HGL-02a, 이슈 #242): ChoJung이면 → ChoJungJongJong(갉), 그 밖이면 앞 글자를 끝내고 낱자 겹자음 하나(ㄺ). 낱자 + 모음 = 앞 자음 낱자 + 새 글자(ㄺ + ㅏ = ㄹ가). 받침에 붙은 겹받침은 입력 단위 목록에 두 자음(ㄹ, ㄱ)으로 쌓아 ⌫ = 둘째 자음만(갉 ⌫ = 갈, 두 번 치기와 같음), 낱자는 한 단위라 ⌫ 한 번에 통째로(PM 결정 2026-11-02, 이슈 #242, 원칙: 두 번 치기와 같은 결과)
 · 모음 연속(두벌식 키): 정책의 병합 표에 있으면 중성 교체, 없으면 새 글자
 · ReplaceVowel(v): 조합 중 글자의 중성을 v로 바꿈(그래피티 천지인: ㅣ → ㅏ → ㅑ)
 · UndoLast: 입력 단위 목록에서 마지막 하나를 되돌림(조합 중 글자 안에서만, 확정 경계를 넘지 않음)
 · Backspace: 정책대로(위 표). 조합 없음이면 앱이 확정 글자 한 글자 삭제. 누르고 있으면 반복(첫 지연 후 일정 간격, 반복 한 번 = Backspace 한 번, FR-CMN-07c)
```

## 5. 그래피티 처리 흐름

```
MotionEvent → InkCollector(포인터 ID별, 점 열, 영역: 문자/숫자)
   ▼ ACTION_UP
recognizer.Recognizer.recognize(stroke, 영역, GraffitiState)
   ├─ 탭 / 짧은 세로선 / 짧은 가로선  → 규칙 판정(길이·방향)
   ├─ 제어 획(스페이스, 백스페이스, 리턴, 시프트, 캡스록, 확장 시프트 사선, V, J) → 규칙 + 템플릿
   └─ 글자 획 → 대기 집합 → 영역·언어별 기본 집합 순으로, 집합마다 글자별 합산 점수(템플릿 점수 + 신경망 점수)의 최고 글자. 문턱 미만이면 다음 집합(5.1)
   ▼
recognizer.GraffitiState(시프트, 캡스록, 확장 시프트 대기, 구두점 시프트 대기, 내부 언어(한/영, 시작 = 한글))
   ├─ 영문·숫자·기호 → 이벤트 Commit(문자)  (한글 조합 중이면 먼저 Finish)
   ├─ 한글 자음(쌍자음 포함) → JamoEvent

- **패드 상태 표시(SRS FR-GRF-05d, GRAFFITI 4.2, 이슈 #136):** `GraffitiPadView`는 획을 처리할 때마다(그리고 초기화 뒤) `GraffitiState`의 내부 언어·시프트·캡스록·구두점 시프트 대기·확장 시프트 대기를 읽어 다시 그린다. 문자 영역 왼쪽 위 구석 탭 영역에 점과 언어 글자("한"/"A"), 패드 구석 한 자리에 켜진 대기 표시(⇧·⇪·•·↘). 상태는 `GraffitiState`가 정본이고 뷰는 그리기만 한다. 인식 글자 표시(FR-GRF-07)와 달리 비밀번호 입력창에서도 그린다. 위치·크기·그림은 LLD-05 8.1.
- **인식 영역 경계(SRS FR-GRF-01a, FSS#48):** `GraffitiPadView`는 `GraffitiPadGeometry`의 문자 영역·숫자 영역 사각형을 조금 안으로 줄인 둥근 사각형 테두리를 그린다. 영역 사이·패드와 보조 줄 사이의 구분선은 두 테두리의 틈이 대신한다. 구석 점·언어 글자·대기 표시는 테두리 안으로 옮긴다. 영역 판정(`areaAt`, 시작점의 x)과 영역 크기는 바꾸지 않으므로 테두리와 영역 끝 사이 틈에서 시작한 획도 그 영역 획이다. 상태와 상관없는 그림이라 비밀번호 입력창에서도 그린다. 입력 연습은 같은 뷰를 쓴다. 여백·두께·색은 LLD-05 8.1.

- 그래피티 안의 한영 전환은 `GraffitiState`의 내부 언어만 바꾼다. 모드 키(FR-CMN-03)와 별개다(FR-GRF-05a).
- **ㆍ 중간 상태(FR-HGL-04e):** 첫 요소가 탭이라 모음이 성립하지 않은 동안(ㆍ, ‥)은 `CheonjiinAssembler`만 상태를 갖고 조합기에는 아무것도 넘기지 않는다. 앱은 조합 텍스트 뒤에 임시 글자(탭 한 번 ㆍ U+318D, 두 번 ‥ U+2025)를 붙여 `setComposingText`로 보인다. ㅣ·ㅡ로 모음이 성립하면 그때 `Vowel`을 넘긴다(도깨비불도 이때). 성립 전에 자음·스페이스·엔터·확정 획·모드 전환이 오거나 그 밖의 이유로 조합을 확정하면(숫자 영역 획, 영문·기호, 그래피티 안 한영 전환, 커서 이동, 입력창 변경) 조립기를 비우고 임시 글자를 버린다(DCR-21). 성립한 모음 뒤에 이어질 수 없는 요소(ㅐ + 탭, ㅣ + ㅣ, ㅡ + ㅡ 등)는 조립기가 무시한다. 상태·표시를 바꾸지 않고 요소 목록에도 넣지 않으며, `GraffitiPadView`의 인식 글자도 그리지 않는다(DCR-04, 오너 결정 #74 A). ‥ 다음 세 번째 탭은 시작하는 모음이 없으므로 무시한다(‥ 그대로). 조합 중인 글자가 없을 때의 탭도 같은 규칙으로 "ㆍ"만 표시하고, 모음이 성립하면 모음 단독 글자가 된다(ㆍ + ㅣ = ㅓ).
- **⌫ 순서(FR-CMN-07b):** ⌫는 먼저 조립기에 묻는다. 조립기에 요소가 있으면(ㆍ·‥ 임시 상태 포함) 조립기가 마지막 요소 하나를 빼고, 남은 요소로 모음을 다시 계산한다. 결과에 따라 조합기는 따라간다: 남은 요소가 모음이면 `ReplaceVowel`, 모음이 아니게 되면(거 → ㄱㆍ) 조합기의 그 `Vowel`을 되돌리고 임시 글자 표시로 바뀐다. 조립기에 요소가 없을 때만 조합기의 입력 단위 목록에서 뺀다. **조립기는 모음이 성립한 뒤 자음(받침)이 오면 닫혀 비워진다.** 닫힌 모음은 다시 열지 않으므로, 받침을 ⌫로 지운 뒤의 탭은 새 요소로 시작한다(각 ⌫ = 가, 이어서 탭 = 가ㆍ). 조립기의 요소 목록은 확정·닫힘 때 버린다. 그래서 가 ⌫ = 기(조립기 ㅣ), 이어서 탭 = 가 / 와 ⌫ = 외 / 각 + 탭 = 각ㆍ, ⌫ = 각 / 각 ⌫ = 가. 쌍자음(시프트 획 + 자음)은 자모 하나라 ⌫ 한 번에 지운다.
- **시프트 대기 중 ⌫:** 시프트·확장 시프트·구두점 시프트 대기 상태에서 ⌫를 누르면 대기만 취소하고 글자는 지우지 않는다(SRS 백스페이스 사례, DCR-05).
- **`GraffitiState` 시프트 규칙(SRS FR-GRF-05c, DCR-05):** 영문 캡스록 중 시프트 획 → 캡스록 끔(시프트 대기 없음). 한글 시프트 두 번 → 시프트 끔. 시프트가 쓰일 곳이 없는 획(쌍자음 없는 자음, 모음 요소, 숫자 영역 획) → 시프트 없이 해석하고 시프트 소멸. 대기 중 다른 제어 획 → 그 동작 + 대기 소멸. 대기를 만드는 획(시프트, 확장 시프트 사선, 구두점 시프트 탭)과 한영 전환 획도 제어 획이다 → 앞 대기를 지우고 자기 동작(새 대기, 전환). 판정 순서는 확장·구두점 대기의 기호표 획(직선·탭 모양 획도 기호표에 실리면 여기서 기호, 실리지 않으면 평소 뜻대로 아래 단계로, 확장 기호표에 탭은 없다, ⌫ 획(←)은 기호표에 싣지 않아 늘 대기 취소 — 오너 결정 #79 OD-3 A, GRAFFITI 4.2·6.2-8, 설계질의 #79. 기호표는 모양으로 찾고 길이로 가르지 않으며, 문자 영역 구석 탭은 기호표의 탭 `.`과 다른 획이라 한영 전환으로 간다 — GRAFFITI 6.4·6.5) → FR-GRF-05 조합(사선 + 탭 = 한영 전환, 영문 시프트 두 번 = 캡스록)·05c ①② → 그 밖의 제어 획(FR-GRF-05c ⑥, 설계질의 #6 Q2). 확장·구두점 대기 뒤 기호표에 없고 제어 획도 아닌 획 → 대기 소멸 + 평소대로 해석(05c ⑦, 오너 결정 #6 OD-2). 그래서 영문 대문자 = 캡스록 또는 시프트(둘이 함께 켜진 상태는 생기지 않는다).
- **한영 전환(DCR-06):** 그래피티 안의 한영 전환 획은 먼저 조합을 확정하고(임시 글자 버림) 내부 언어를 바꾼다. 모드 전환과 같은 처리다.
- **인식 실패(DCR-07):** 어느 획에도 맞지 않으면 입력 없이 `Feedback` 오류 진동만 낸다(SRS FR-GRF-08).
- **인식 글자 표시(FR-GRF-07):** 비밀번호 입력창에서만 그리지 않는다(FR-CMN-08 ①, DCR-19). 학습 금지 입력창에서는 그린다(FR-CMN-08 ②: 학습 금지는 학습·통계·기록만 끄고 표시는 끄지 않음, 오너 원칙 "학습 금지이지 암호처럼 출력 금지가 아니잖아!"). 그리는 것은 이번 획이 뜻하는 글자(자모·천지인 요소·영문 글자·숫자·기호, 시프트로 바뀐 글자)뿐이다. 글자가 없는 획(스페이스, ⌫, 리턴, 'J', 한영 전환, 대기 획), 인식 실패, 조립기가 무시한 천지인 요소(FR-HGL-04c)는 그리지 않는다(오너 결정 #74 A). 대기 상태 표시(GRAFFITI 4.2)는 이와 별개다(설계질의 #74).
- **초기화:** 모드 전환, 커서 이동, `onStartInputView`, 확정('J' 획 포함) 때 `CheonjiinAssembler`를 비우고 `GraffitiState`의 일회성 상태(시프트, 확장 시프트 대기, 구두점 시프트 대기)를 비운다. 캡스록과 내부 언어는 커서 이동·확정에서는 유지하고, 그래피티 모드에 새로 들어올 때 기본값(캡스록 끔, 한글)으로 돌린다.
- 숫자류 입력창(숫자·전화·날짜시간·비밀번호)에서는 그래피티가 아니라 영문 쿼티로 시작하므로(FR-CMN-04, 8.1) 숫자 입력창 전용 패드는 없다.
- **보조 줄:** 왼쪽부터 모드 키(72dp, 탭 자판 모드 키와 같음), 스페이스, ⌫, ↵. 모드 키 뒤 세 버튼은 남은 폭을 같게 나눈다(FR-GRF-01, DCR-12). 기능키는 누를 때 처리한다(FR-CMN-11a). 모드 키만 손을 뗄 때 탭(모드 전환) / ↑(설정 열기)를 가르고(8.2절), 모드 키에서 시작한 포인터는 패드 획으로 넘기지 않는다(위로 그어 패드에 들어가도 인식기에 주지 않음).
- 템플릿은 JSON(앱 리소스). 한글 자음과 영문 글자는 정본 표를 보고 그린 템플릿에 오너 손 획을 더한다(인식 전용, ㅋ과 영문 u 2획·d 4획 제외, 판정 코드 그대로, SRS FR-GRF-03b). 한 획 쌍자음 템플릿은 두지 않는다(쌍자음 = 시프트 + 자음, SRS FR-GRF-03a). 영문 글자·숫자·구두점·확장 기호 템플릿은 영문 단일 획 표(GRAFFITI 6.1·6.3·6.4, SRS FR-GRF-02, 오너 결정 #79 OD-1·OD-2 A)를 보고 그린다. 겹치는 모양의 처리는 GRAFFITI 6.5대로다(오너 결정 #79 OD-4~OD-7 A: 구두점 대기 + ↘ = `\`, 대기 뒤 어느 영역이든 기호표 모양이면 기호, 영문 K = 원본 α 고리, `•` 없음). 표의 미확인 획은 확정 전까지 T28 임시 템플릿을 유지한다. 개발용·평가용 획 샘플은 시험 데이터에 따로 둔다(NFR-09).
- **획 안내표 팁(SRS FR-GRF-09~09d, GRAFFITI 6.6, 이슈 #189):**
  - **데이터 = `recognizer.GuideCatalog`(JVM):** 언어와 상관없이 늘 같은 칸 목록 하나를 낸다(SRS FR-GRF-09b, 오너 보충 "영문과 한글 숫자를 한번에 표시해도 돼. 참고니까."). 구획 순서는 한글 → 영문 → 숫자 → 제어 획(공통 + 언어별 표시) → 기호(57, SRS TBD-26 확정)로 고정이다. 칸 = 정본 표의 한 행(①, 원본에 있으면 ②)이고, 그릴 모양은 **내장 `TemplateSet`의 템플릿 id**(점 열, 시작점이 첫 점) 또는 **규칙 획 종류**(↓ → ← ↑ ↙ ↘, 탭, 구석 탭, 두 번 긋기, 이어 쓰기)로 가리킨다. 한글 칸은 `KO_LETTER`, 영문 칸은 `EN_LETTER`, 숫자는 `NUMBER`, 기호는 `PUNCT`·`EXTENDED` 집합에서 찾으므로 같은 모양 다른 뜻(영문 K와 한글 ㅈ 등)도 각 구획의 칸으로 따로 나온다. 인식기와 같은 템플릿을 쓰므로 보이는 획과 인식하는 획이 어긋나지 않는다. 인식 여유용 템플릿 변형과 오너 획 템플릿(SRS FR-GRF-03b)은 칸이 아니다. 임시(T28 interim) 템플릿을 가리키는 칸은 `interim` 표시를 갖고, 템플릿이 없어 인식되지 않는 획은 목록에 넣지 않는다(SRS TBD-11). 행 ↔ 템플릿 id 목록과 임시 표시를 런타임에 읽는 방법은 LLD-05에서 정한다. 시험: 모든 칸이 실제 템플릿이나 규칙 획으로 풀리는지, 구획 순서·구획별 칸 수, 임시 표시가 `TEMPLATES.md`의 interim과 같은지(JVM).
  - **그리기 = `GraffitiGuidePanel`(app, Canvas, 불투명 덮개):** 칸마다 획 선, 시작점 ●, 끝 방향 화살표, 뜻 글자를 그리고, 오른쪽 위 구석에 ✕를 그린다. 임시 칸은 점선 + "임시". 그림은 직접 그리고 비트맵은 쓰지 않는다(CON-6, FR-GRF-05d와 같은 원칙). 덮개 안 끌기는 세로 스크롤만 하고 입력·`GraffitiState`와 무관하다.
  - **소유·열기·닫기:** **빈 띠를 소비하는 `KeyboardRootView`**(창 높이 고정·바닥 정렬·빈 띠, LLD-08 7절)가 띠 오른쪽 끝의 안내표 버튼(1줄 × 1줄)과 덮개(`GraffitiGuidePanel`)를 가진다. `GraffitiPadView`는 5줄(패드 + 보조 줄) 그대로다. 버튼과 ✕는 키이므로 피드백을 누를 때 낸다(FR-CMN-11a ② 예외). 버튼은 누를 때 처리하고, ✕는 덮개 오른쪽 위에 고정(스크롤을 따라가지 않음)하고 손을 뗄 때 ✕ 안이면 닫는다. 누른 뒤 ✕ 밖으로 끌면 닫지도 스크롤하지도 않는다(FR-CMN-11a ① 예외, 세부는 LLD 몫). 이 소유에 맞춘 LLD-05·LLD-08 갱신은 개발 단계 몫이다. 열림 상태는 입력기 뷰가 가진 화면 상태일 뿐이고 `GraffitiState`·조합기·조립기에 아무것도 넘기지 않는다(그래서 조합 확정·초기화의 원인이 아니다). 닫는 때: 버튼, ✕, 그래피티 모드를 떠남(`ModeController`), `onFinishInputView`. 설정 변경(화면 회전 등)으로 `onCreateInputView`가 뷰를 다시 만들면 열림 상태를 되살리지 않고 닫힌 상태로 시작한다(세부는 LLD 몫). 덮개의 다른 곳 탭은 닫지 않는다(스크롤 끌기와 섞이지 않게).
  - **배치와 터치(오너 정정 #189, SRS TBD-25·FR-GRF-09a):** 덮개는 `GraffitiPadView`(패드 + 보조 줄, 5줄)와 같은 자리에 그 위로 겹쳐 놓는다. 빈 띠와 버튼은 덮지 않는다. **창 높이·인셋은 바뀌지 않는다**(5A 창 높이 규칙 그대로, 세로·가로 같음). 열린 동안 `KeyboardRootView`가 덮개 자리의 터치를 모두 덮개로 보내고 아래 `GraffitiPadView`(패드·보조 줄·모드 키)에는 보내지 않는다. 열 때 `GraffitiPadView`에 진행 중인 포인터가 있으면 결과 없이 버리게 한다(`ACTION_CANCEL`과 같은 처리: 획은 인식하지 않고 오류 진동도 없음, 보조 줄 키 반복은 멈춤, FR-CMN-11a ③). 조합·대기·언어 상태는 건드리지 않는다.
  - **입력창 종류:** 비밀번호·학습 금지 입력창에서도 그린다(`sink.restricted`를 보지 않음, FR-GRF-09d). 안내표는 아무것도 저장하지 않는다.

### 5.1 글자 획 인식: 템플릿 점수와 신경망 점수의 합산 (SRS FR-GRF-10~14, FSS#96)

오너 결정(2026-11-14, FSS#96)에 따라 한 획 그래피티를 유지하고, 규칙 획이 아닌 획을 **템플릿 점수와 신경망 점수의 합산**으로 가른다. 템플릿은 버리지 않는다.

```
InkStroke(패드 dp 원 표본 점 열, 시작한 영역)
   ▼
StrokeRules: 탭 / 구석 탭 / 직선·사선 ── 맞으면 여기서 끝(대기 중이면 그 기호표의 규칙 항목이 먼저 — 지금 그대로)
   ▼ 규칙 획이 아님
집합 고르기(지금 그대로): 대기 중이면 PUNCT 또는 EXTENDED → 문턱 미달이면 영역·언어의 기본 집합(KO_LETTER / EN_LETTER / NUMBER)
   ▼ 집합 하나마다
   ├─ 템플릿 쪽: TemplateMatcher 점수(재표본·정규화·평균 점 거리, 모서리 수 보정, 닫힌 고리 — 지금 그대로)
   │      글자별 템플릿 점수 = 그 글자의 내장 템플릿과 개인 템플릿 가운데 최고
   ├─ 신경망 쪽: 특징 계산(8 × 8 격자 × 방향 9 = 값 576개) → 몸통 순전파 → 임베딩
   │      글자별 신경망 점수 = 임베딩과 그 글자의 예시 임베딩(출고 예시 + 개인 획) 사이 코사인 가운데 최고
   └─ 합산: 글자별 a × 템플릿 점수 + (1 − a) × 신경망 점수(a = 0.5) → 최고 글자
          문턱 둘: 그 글자의 합산 점수 ≥ 0.80 그리고 이 집합의 템플릿 최고 점수(글자 무관) ≥ 0.78 → StrokeToken.Symbol, 아니면 다음 집합
   ▼ 끝까지 없음
StrokeToken.Unknown(인식 실패, SRS FR-GRF-08)
```

- **바뀌지 않는 것:** `Recognizer`의 규칙 우선, 집합 순서, 대체 동작(대기 집합 → 기본 집합 → `Unknown`), `StrokeToken`, `GraffitiState`, `CheonjiinAssembler`, `TemplateMatcher`의 점수 계산. 바뀌는 것은 집합 하나에서 글자를 고르는 방법과 문턱 조건뿐이다(0.77까지는 템플릿 최고 점수 하나와 문턱 0.80 하나).
- **글자 = 분류 단위:** 한 집합에서 출력이 같은 템플릿들이 글자 하나다(템플릿 id가 여러 개여도 글자는 하나). 템플릿 획이 없는 규칙 항목(기호표의 탭·직선 기호)은 글자가 아니고 규칙이 받는다. 지금 구성은 한글 글자 집합 16(자음 14 + 스페이스 V + 확정 J), 영문 글자 집합 25(i는 직선 규칙), 숫자 집합 9(1은 직선 규칙)이고 구두점·확장 집합은 템플릿 획이 있는 기호들이다. 인식 결과로 돌려줄 템플릿 id(고른 글자의 어느 id인지)는 LLD-05가 정한다.
- **구성 요소(이름은 LLD-05가 정한다):**

| 구성 요소 | 모듈 | 하는 일 |
|---|---|---|
| 특징 계산 | `recognizer` | 획의 원 표본 점 열 → 값 576개(SRS FR-GRF-12). 획의 둘레 상자 기준 8 × 8 격자, 방향 8채널(이웃 두 방향에 나눠 담음, 칸 안 경로 길이, 1에서 자름) + 가운데 1채널(원 표본의 1dp 미만 걸음, 4걸음 = 1, 1에서 자름). 학습 쪽 계산과 같아야 한다 |
| 순전파 | `recognizer` | 모델 리소스(몸통 가중치, 32비트 부동소수, **집합마다 몸통 하나씩 5개**)를 읽어 특징 → 그 집합 몸통의 임베딩. 외부 라이브러리 없이 Kotlin으로 계산한다. 마지막 분류 층은 쓰지 않는다 |
| 예시 저장소 | `recognizer`(메모리) | 집합·글자별 예시 임베딩. 출고 예시(리소스: 글자당 합성 예시 32개 + 내장 템플릿에 든 것과 같은 오너 손 획 — 영문 156획, 한글 117획)와 개인 획에서 계산한 임베딩을 함께 갖는다 |
| 합산 | `recognizer` | 글자별 두 점수 → 합산(a = 0.5) → 최고 글자 → 문턱 둘(합산 점수 ≥ 0.80, 그 집합의 템플릿 최고 점수 ≥ 0.78. SRS FR-GRF-10 ④). 값은 상수이고 한 쌍을 모든 집합에 쓴다(집합별로 고르지 않았다). 출처는 FSS#96 작업지시서 v2(SRS TBD-34 ①), 상수 이름과 자리는 LLD-05 |
| 개인 획 저장소 | `app` | 개인 획 파일 읽기·쓰기(7.4). 안드로이드 의존은 여기와 화면뿐이다 |
| 학습 화면 | `app` | `PracticeActivity`의 "내 획 학습" 주제(7.4) |

- **모듈 경계:** 특징 계산·순전파·예시 보관·합산은 `recognizer`에 둔다(안드로이드 의존 없음, JVM 시험, NFR-08). 파일 저장과 화면은 `app`이다.
- **개인 획 넣기:** `app`이 저장소에서 읽은 개인 획 목록(집합, 글자, 점 열)을 `recognizer`에 넘기면, `recognizer`가 획마다 개인 템플릿(템플릿과 같은 정규화, 모서리 수)과 임베딩을 계산해 **새 인식 구성을 통째로 만들어 바꾼다.** 획 하나를 인식하는 도중에는 구성이 바뀌지 않는다(바꾸는 방법은 LLD-05). 개인 획은 기본 집합(한글 글자, 영문 글자)에만 들어가고 다른 집합의 구성은 그대로다(SRS FR-GRF-14 ①). 내장 템플릿과 출고 예시는 지우지 않으므로 개인 획 목록이 비면 출고 상태와 같다.
- **서비스 연결:** `KeyboardService`는 그래피티 인식기를 만들 때와 키보드가 뜰 때(`onStartInputView`) 저장소가 바뀌었으면 다시 읽어 넘긴다(SRS FR-TUT-17 ③). `PracticeActivity`의 그래피티 연습 주제와 학습 화면도 같은 저장소의 개인 획을 넣은 인식기를 쓴다. 실제 입력 경로는 저장소를 읽기만 한다(7.4).
- **모델 자산:** `recognizer` 모듈의 리소스(템플릿 JSON과 같은 자리)에 몸통 가중치와 출고 예시를 싣는다. **몸통은 집합마다 따로 5개다**(SRS FR-GRF-13 ②: 하나를 함께 쓰면 한글 손가락 출고가 −2.4 %p였다. 통계로는 구분되지 않으나 방향이 한쪽이었다). 그래서 대기 중에 두 집합을 차례로 찾으면 순전파가 두 번이다. 크기는 32비트 부동소수로 몸통 5개 약 460 kB + 예시 약 400 kB = 약 862 kB다. 파일 형식은 LLD-05가 정한다. 템플릿 집합의 글자 목록과 예시의 글자 목록은 같아야 하고 시험으로 지킨다(11.1). 템플릿의 글자 구성이나 내장 템플릿의 오너 획을 바꾸면 모델과 예시를 다시 만든다.
- **다시 만들기:** 저장소 `tools/`의 스크립트가 합성 획 생성 → 학습 → 모델 파일·출고 예시·시험용 고정 표본을 만든다. **가중치는 합성 획만으로 학습한다**(사용자 획과 오너 손 획은 가중치에 들어가지 않는다, SRS FR-GRF-13 ⑤). 출고 예시에 넣는 오너 손 획은 저장소에 이미 있는 내장 템플릿용 파일에서 읽는다(사람 손 획을 새로 올리지 않는다). 절차 문서도 `tools/`에 둔다.
- **읽는 때:** 모델과 출고 예시는 템플릿 JSON처럼 인식기를 만들 때 읽는다. 읽는 시간은 폰에서 재지 않았다. 키보드가 처음 뜨는 것을 늦추지 않게 하는 방법은 LLD-05가 정한다(10.1 R14).
- **결정성(NFR-04):** 가중치는 고정이고 난수·시계를 쓰지 않는다. 같은 획과 같은 개인 획 목록에는 같은 결과다.
- **실패 처리:** 개인 획 파일을 읽지 못하면 개인 획 없이 인식한다(SRS FR-TUT-15 ④). 한 획의 특징 계산·순전파에서 예외가 나면 그 획을 무시하고 오류 기록만 남긴다(9장, NFR-03. 획 좌표는 기록하지 않는다).

**측정 근거와 한계(PM 측정 2026-11-14, FSS#96 작업지시서 v2. 앱 밖 측정).** 자료는 FSS#82와 같은 한 사람의 한 획 자료다(손가락 이틀~사흘, 펜 하루, 폰 한 대). 아래 수치는 그 작업지시서의 것이다.

① 가르치는 날과 다른 날의 획으로 잰 정확도(%, 출고 / 글자당 1획 / 3획을 가르친 뒤. 시드 5개, 설정은 가르치는 날 안에서 고름):

| | 영문 손가락 | 영문 펜 | 한글 손가락 | 한글 펜 |
|---|---|---|---|---|
| 템플릿 단독 | 91.7 / 95.6 / 97.6 | 80.0 / 87.7 / 89.9 | 91.7 / 98.9 / 100.0 | 90.5 / 94.5 / 96.3 |
| 8 × 8 × 방향 9 단독 | 94.0 / 96.3 / 98.3 | 93.1 / 95.6 / 97.1 | 94.5 / 97.6 / 99.6 | 92.9 / 96.1 / 97.7 |
| 8 × 8 × 방향 9 + 템플릿 합산 | 97.5 / 98.9 / 99.5 | 96.6 / 97.9 / 98.0 | 98.2 / 99.2 / 100.0 | 95.6 / 96.8 / 98.2 |
| 8 × 8 × 방향 8 + 템플릿 합산(견줌) | 97.6 / 99.4 / 99.5 | 95.1 / 98.1 / 98.3 | 98.0 / 99.5 / 100.0 | 95.4 / 97.1 / 99.2 |

- **방향 9와 8은 구분되지 않는다.** 합산에서 같은 획끼리의 차이는 −1.0 ~ +1.4 %p이고, 유의한 시드는 24칸 가운데 한 칸(한글 손가락 출고)의 5개 중 1개뿐이다. 오너 결정대로 9를 쓴다. 낫다는 근거도 나쁘다는 근거도 없다. 합성 학습 획에 짧은 걸음이 거의 없어 가운데 채널이 학습 때 비어 있다는 사정은 그대로다.
- **가르친 획이 다른 글자를 가져감**(틀린 획 하나만 가르쳤을 때 다른 날 다른 글자를 잃은 획 수, 시드 평균): 템플릿 단독 영문 3.0 / 한글 0.0, 방향 9 합산 0.2 / 0.0.

② 출고 구성(지금 내장 템플릿 + 신경망, a = 0.5, 문턱 둘, 출고 예시에 오너 획 포함. 시드 0 한 모델)에서 맞힌 획 수와 합성 낙서를 받아들인 비율:

| | 사람 획 719 | 합성 획 1,872 | 고리 864 | 합성 낙서 받아들임: 영문 / 한글 |
|---|---|---|---|---|
| 지금(템플릿 단독, 문턱 0.80) | 709 | 1,785 | 863 | 15 % / 8 % |
| 합산(이 구성) | 719 | 1,872 | 863 | 14 % / 5 % |

- **이 표는 고른 뒤의 값이다.** 두 문턱을 이 표의 자료 자체로 골랐으므로 따로 떼어 둔 시험이 아니다.
- 사람 획 719 가운데 영문 손 이틀 치와 한글 손 11-05 낮 치는 내장 템플릿과 출고 예시에 들어 있는 획이라 교차 시험이 아니다. 교차인 것만 보면(템플릿 단독 → 합산): 템플릿에 넣지 않고 남겨 둔 실기 획 74획 중 72 → 74, 영문 펜 90획 중 85 → 90, 한글 펜 42획 중 42 → 42, 한글 손 다른 날 84획 중 84 → 84다.
- 합성 획은 신경망 학습 획과 같은 생성기에서 나와 비교 근거가 아니다(회귀 확인용).
- **템플릿 문턱을 둔 까닭:** 합산 문턱 하나만으로는 영문 합성 낙서의 45 %가 받아들여졌다(템플릿 단독 15 %).
- **출고 예시에 오너 획을 넣는 까닭:** 합성 예시만 넣으면 한글 손 다른 날 84획 가운데 81획을 맞혀 템플릿 단독(84획)보다 못했고, 내장 템플릿과 같은 오너 획을 예시에 더하면 84획이다.
- **기록된 세 사례**(이 구성에 그 획만 가르침. 가르치기 전 → 뒤): ㅋ을 가르친 뒤 태블릿 ㄱ 15획 — 템플릿 단독 15 → 13, 합산 15 → 15. u를 가르친 뒤 실기 V 10획 — 10 → 9, 10 → 10. d를 가르친 뒤 고리 432개 — 431 → 427, 432 → 432.

- **개인 획 반영 방식:** 임베딩 최근접(예시 추가)이다. 신경망의 마지막 층을 기기에서 다시 학습하는 방식은 앞선 측정(FSS#82)에서 다른 글자를 더 잃어 쓰지 않는다.
- **한계:** 한 사람 자료다. a와 두 문턱은 그 사람의 획으로 골랐다. 숫자·기호·제어 획의 사람 표본, 사람이 쓴 낙서, 폰 실행 시간은 없다. 다른 사람의 글씨로 재지 않았다. 글자당 8획까지 가르쳤을 때의 영향도 재지 않았다(잰 것은 1획·3획).

## 5A. 탭 자판 (TapKeyboardView)

- **배치(FR-TAP-03. 폭 수치는 배치 단위다 — 한 줄 360 = 10칸이고 실제 폭은 자판 폭 W에 비례한다):** 편집 줄(Esc ⇥ ← ↑ ↓ → Del ⌫, 8 × 45) + 숫자 줄(10 × 36) + 글자 3줄(10 × 36 / 빈칸 18 + 9 × 36 + 빈칸 18 / 빈칸 18 + 7 × 36 + `=` 36 + ↵ 54) + 기능키 줄(한/영 72 · 스페이스 180 · `,` 36 · `.` 36 · `/` 36) = 6줄(이슈 #198: 기호 키 없음, ⌫는 편집 줄 오른쪽 끝, ↵는 아랫글자 줄, `=` 키(← `-`, FSS#62)는 m 오른쪽, `/`는 맨 아랫줄 오른쪽 끝). Esc·Del은 방향키처럼 조합을 확정한 뒤 `KEYCODE_ESCAPE`·`KEYCODE_FORWARD_DEL`을 보낸다(FR-TAP-13·14). Del은 ⌫·방향키와 같은 반복을 쓴다(잠정, TBD-27). 빈칸은 같은 줄의 가장 가까운 키로 친다(SRS 3.3). ⇧·캡스록·?123·가ABC 키 없음. 줄 높이는 설정값(기본 48dp, FR-SET-06).
- **기호 배정(FR-TAP-03a):** 키 데이터에 방향별 배정(탭, ↑, ←, →, ↓)을 둔다. `stroke-core`가 판정한 방향으로 배정을 찾고, 없으면 탭과 같게 처리한다. 숫자·기호를 넣기 전에 조합을 확정한다(FR-TAP-11a). **두벌식 겹받침 배정(SRS FR-TAP-02c, 이슈 #242):** 두벌식 자음 키(ㄱ·ㄴ·ㄹ·ㅂ·ㅅ·ㅌ·ㅍ)의 방향 배정에 겹받침 자모를 두고(어느 키의 어느 방향인지는 SRS 두벌식 겹받침 배정표가 정본 — FSS#97로 여섯 개의 방향이 바뀌었고 이 문단의 구조는 그대로다. ↑는 시프트 자모가 먼저이고 없으면 겹받침, 그 밖의 방향은 겹받침이 먼저이고 없으면 배정 기호), 그 결과는 기호가 아니라 **자모 이벤트(겹받침 하나)**로 `HangulComposer`에 보낸다(조합을 확정하지 않음, 입력 단위 하나). 쿼티 배치 데이터에는 없다. 변 가운데 표시(FR-TAP-03b)는 같은 데이터에서 그린다 — 쿼티 ↑ 대문자, 두벌식 ↑ 시프트 자모도 키 데이터의 ↑ 결과에서 그린다(탭과 같은 글자·배정 없음·문지르기 결과는 그리지 않음, 이슈 #198).
- **배치는 데이터로 정의**한다(키 목록: 위치·크기·종류·글자·방향별 배정). 쿼티와 두벌식이 같은 뷰와 같은 형식을 쓴다. 따로 만든 숫자 키패드는 없다(숫자류 입력창은 쿼티, FR-CMN-04).
- **창 높이·바닥 정렬:** 키 영역 높이는 모드 중 가장 높은 자판(쿼티·두벌식 6줄)으로 고정한다. 낮은 자판(그래피티 패드)은 바닥에 맞춰 그리고 위 띠는 비운다. 빈 띠는 터치를 소비하되 입력이 없다(그래피티 띠 오른쪽 끝의 획 안내표 버튼만 예외, 5장). 모드 키는 모든 모드에서 맨 아랫줄 왼쪽이라 화면 위치가 같다. **띄운 자판(SRS FR-CMN-15, FSS#86)**에서는 키 영역이 입력 뷰의 바닥이 아니라 **자판 판 안**(손잡이 띠 아래)에 놓이고 입력 뷰는 그보다 높다(아래 "띄운 자판"). 키 영역 6줄 고정, 낮은 자판의 바닥 정렬, 빈 띠, 모드 키 위치는 자판 사각형 안의 규칙이라 그대로다.
- **시스템 막대 여백(SRS FR-TAP-03 아래 창 규칙, 오너 결정 #93 OD-1·2·3 A):** 입력 뷰는 창 인셋 중 내비게이션 바(`navigationBars`)와 시스템 버튼 줄(`tappableElement`)을 **변마다 큰 값**으로 받아 안쪽 여백으로 둔다. 키 영역(6줄 고정 높이, 낮은 자판은 그 안에서 바닥 정렬)은 여백 안쪽에 그리고, 여백은 키보드 배경색으로 칠한다. 아래 변은 늘, 옆 변은 가로 화면 3버튼 내비게이션처럼 막대가 옆에 올 때 같은 방식으로 비운다. 여백은 빈 띠와 같이 터치를 소비하되 입력이 없다. 창 높이 = 6줄 + 아래 여백. **자판을 줄여 남는 자리가 있으면(FSS#85)** 여백 가운데 **자판 판에 드는 부분**(자판 사각형 바로 아래, 그리고 자판 사각형이 닿은 쪽의 옆 여백)만 칠하고 터치를 소비하며, 나머지는 투명한 자리다(아래 "자판 판과 투명한 자리"). 여백의 크기와 창 높이는 그대로다. **띄운 자판(FSS#86)**에서는 같은 인셋 값(과 위쪽 인셋)이 칠할 여백이 아니라 **이동 영역의 경계**로 쓰이고, 여백은 칠하지도 터치를 받지도 않는다(아래 "띄운 자판").
- **자판 폭과 정렬, 좌우 여유 칸(SRS FR-CMN-14·FR-SET-09, 오너 결정 2026-11-02, FSS#25, 오너 요청 2026-11-13, FSS#84):**
  - **낱말:** **자판** = 키 10칸(폭 W = 10u). **여유 칸** = 자판 왼쪽 끝·오른쪽 끝 바깥의 띠 둘(폭 m = u / 2씩, 높이 = 키 영역 6줄). **자판 사각형** = 여유 칸 + 자판 + 여유 칸(폭 R = W + 2m = 11u, 높이 = 키 영역 6줄. 그래피티의 빈 띠도 이 안이고, 시스템 막대 여백은 밖이다). **남는 자리** = 가용 폭 A에서 자판 사각형을 뺀 자리. **자판 판** = 키보드가 칠하고 터치를 받는 사각형 하나(자판 사각형의 폭 × 입력 뷰 높이 전체, 자판 사각형이 가용 폭의 끝에 닿은 쪽은 옆 시스템 막대 여백까지). **투명한 자리** = 입력 뷰에서 자판 판 밖(남는 자리와 그 아래 여백, 닿지 않은 쪽의 옆 여백)(FSS#85, SRS 1.3). **띄우기** = 방향별 설정(기본 끔). **붙은 자판** = 띄우기가 꺼진 방향의 자판(0.76 그대로), **띄운 자판** = 켜진 방향의 자판. **손잡이 띠** = 띄운 자판의 자판 사각형 바로 위 띠(폭 R, 높이 = 손잡이 띠 높이 24dp, 키가 아님). 띄운 자판의 **자판 판** = 손잡이 띠 + 자판 사각형(시스템 막대 여백은 들지 않음). **이동 영역 S** = 입력 뷰에서 아래·옆의 시스템 막대 여백과 위의 상태 막대·화면 컷아웃 자리를 뺀 사각형(FSS#86, SRS 1.3·FR-CMN-15).
  - **계산은 순수 함수 하나**(`KeyboardWidth`, 안드로이드 없음, 단위 시험): 입력 = 가용 폭 A(dp, 입력 뷰 폭 − 옆 시스템 막대 여백), 화면 짧은 변 A_v(dp, 세로 화면의 가용 폭), 화면 방향, 세로·가로 설정값(키 한 칸 폭 u 또는 기본값, 정렬) → 출력 = **자판 사각형의 폭 R과 가용 폭 안의 왼쪽 위치 x, 여유 칸 폭 m**(자판 폭 W = R − 2m, 자판 왼쪽 끝 = x + m). 키 한 칸 = 배치 단위 360의 한 칸(자판 한 줄 10칸, 자판 사각형 11칸). 세로 u = 설정값, 없으면 꽉 채움(R = A). 가로 u = 설정값, 없으면 세로의 u(세로가 꽉 채움이면 A_v / 11, 곧 11u = A_v. 아래 식의 하한 352dp와 A에서 멈춤이 그 뒤에 걸린다 — A_v가 352dp보다 작으면 R = min(A, 352)). 설정값은 키 크기 숫자 또는 "꽉 채움"(슬라이더 위 끝, 숫자로 저장하지 않음 — 방향·막대가 바뀌어도 꽉 채움, SRS FR-SET-09)이다. **R = min(A, max(352, 11 × u)), m = R / 22, W = R − 2m.** x = 0(왼손모드), (A − R) / 2(중앙모드), A − R(오른손모드). 0.74까지 저장된 u는 **바꾸지 않고 그대로 읽는다**(W는 같고 R이 u만큼 넓어지며 A에서 멈춘다. 저장 형식·키 이름 그대로, 7.3). 픽셀 반올림은 LLD가 정하되 두 여유 칸의 폭이 같고 m + W + m = R이 정확히 맞아야 한다. 화면 방향은 입력 뷰가 놓인 구성(세로·가로)이고, 설정값은 방향마다 따로다(7.3).
  - **놓기:** 입력 뷰 루트(`KeyboardRootView`)가 잴 때 R·m을 구해 모드 뷰·그래피티 안내표 덮개를 **폭 W**로 재고, 놓을 때 **옆 여백 + x + m**에 둔다. 안내표 버튼은 자판 오른쪽 끝(x + m + W − 버튼 폭)의 빈 띠에 둔다. 높이·바닥 정렬은 그대로다. **여유 칸은 루트의 자리다**(모드 뷰 밖, 자식 없음): 루트가 칠한 키보드 배경색이 보이고 그 밖에는 아무것도 그리지 않는다. 0.75까지는 남는 자리도 같은 루트 배경이었고, 0.76부터 루트는 **자판 판만** 칠한다(남는 자리는 투명한 자리 — 아래 "자판 판과 투명한 자리", FSS#85). **터치:** 여유 칸·빈 띠·자판 판 안의 시스템 막대 여백은 모두 자식 밖이라 루트가 터치를 소비한다(같은 길, 입력·피드백 없음). 남는 자리는 터치 영역 밖이라 거기서 시작한 터치는 창이 받지 않게 한다(플랫폼이 아래 앱으로 보냄 — 실기 미확인, 10장 R11 ②). 안드로이드는 다른 손가락이 자식을 누르고 있으면 자식 밖에 닿은 새 손가락(`ACTION_POINTER_DOWN`)도 그 자식에 붙여 보내므로, 루트는 **자식 밖에서 시작한 포인터를 자식에 넘기지 않는다**(그 포인터의 내려옴을 보내지 않으면 나뉜 이동·올라옴도 자식에 가지 않음, LLD. `OffKeyboardPointers` 그대로 — 여유 칸에서 시작한 포인터도 여기에 든다). 그래피티 위 빈 띠도 같다.
  - **배치·판정 코드에서 바뀌는 것은 테두리의 왼쪽·오른쪽뿐이다:** 모드 뷰(`TapKeyboardView`·`GraffitiPadView`)는 지금처럼 받은 폭 W로 기하(키 사각형, 패드 구역)를 만든다. 그래서 키 폭은 W에 비례해 준다. **입력기 테두리(FR-SWP-45):** 0.74까지는 모드 뷰 좌표의 왼쪽 0·오른쪽 W를 테두리로 보아 끝 키의 바깥쪽 변이 테두리 변(`KeyGeom.outerEdges`)이었다. 0.75부터 모드 뷰는 키 기하를 만들 때 **테두리의 왼쪽·오른쪽을 자판 사각형의 바깥 변(모드 뷰 좌표로 −m, W + m)**으로 준다. 그러면 끝 키의 왼쪽·오른쪽 변은 테두리 변이 아니게 되고, `EdgeCrossingTracker`는 고치지 않아도 그 변을 다른 변처럼 변 너머 `minCrossDp`에서 나감으로 기록한다. 위·아래는 그대로다(모드 뷰의 위 0·아래 높이). 모드 뷰의 모드 키와 그래피티 보조 줄 끝 키도 같은 길이다. 루트가 m을 모드 뷰에 알리는 길과 `KeyGeom` 쪽 매개변수 모양은 LLD가 정한다. 손가락이 여유 칸·남는 자리로 나가도 DOWN을 받은 모드 뷰가 자기 폭 밖 좌표(음수, W 초과)로 이동을 계속 받는다(안드로이드 터치 대상 유지, 10장 R2와 같은 성질). 꽉 채움에서는 여유 칸의 바깥 변이 화면 끝이라 그 너머 좌표는 오지 않지만, m이 `minCrossDp`보다 넓어(u 32dp에서 16dp, 가용 폭 176dp 이상이면 8dp 이상) 화면 끝에 닿기 전에 통과가 선다.
  - **다시 놓기:** 화면 방향이 바뀌면(`onConfigurationChanged`, 8장) 그 방향의 값으로, 설정 흐름(Flow)에서 폭·정렬이 바뀌면 곧 루트가 다시 잰다(줄 높이 설정과 같은 길). 모드·조합 상태는 건드리지 않는다.
  - **자판 판과 투명한 자리(SRS FR-CMN-14 ⑫, 오너 요청 2026-11-13, FSS#85):** 키보드가 **칠하는 자리와 터치를 받는 자리는 같은 사각형 하나(자판 판)**이고, 입력 뷰에서 그 밖은 투명한 자리다. 두 가지(칠하기, 터치 영역)가 따로 자리를 셈하지 않고 **같은 사각형 값**을 쓴다.
    - **사각형 계산(순수 함수, 안드로이드 없음, 단위 시험. 이름과 둘 자리는 LLD — `KeyboardWidth` 곁):** 입력 = 입력 뷰의 폭·높이, 시스템 막대 여백(왼쪽 l·오른쪽 r·아래), 가용 폭 A(= 폭 − l − r), `KeyboardWidth`가 낸 x·R(모두 px). 출력 = 입력 뷰 좌표의 사각형: **왼쪽 = l + x, 단 x = 0이면 0**(자판 사각형이 가용 폭의 왼쪽 끝에 닿음 → 왼쪽 옆 여백까지), **오른쪽 = l + x + R, 단 x + R = A이면 입력 뷰 폭**(오른쪽 옆 여백까지), **위 = 0, 아래 = 입력 뷰 높이**(키 영역 6줄 + 아래 여백). 옆 여백이 없으면(l = r = 0) 왼쪽·오른쪽은 자판 사각형의 변과 같다. 꽉 채움(R = A)이면 사각형 = 입력 뷰 전체다. **"닿음" = 그쪽 남는 자리의 폭이 0px**이다(왼쪽 x = 0, 오른쪽 A − x − R = 0. 칠하고 놓는 데 쓰는 것과 같은 px 값으로 판정 — 반올림은 LLD). 그래서 중앙모드에서 A − R이 1px이라 한쪽만 0px이 되면 그쪽만 닿은 것이다. 사각형이 가로 구간이 아니라 사각형(위·아래 포함)인 것은, 뒤에 자판 사각형의 세로 자리를 바꾸는 작업(FSS#86)이 같은 값을 그대로 쓰게 하려는 것이다.
    - **칠하기:** `KeyboardRootView`는 뷰 전체 배경(0.75까지 `setBackgroundColor`)을 두지 않고 **자판 판만** 키보드 배경색으로 칠한다(방법은 LLD). 그래서 여유 칸·그래피티 빈 띠·자판 사각형 아래 여백(과 닿은 쪽 옆 여백)은 지금처럼 배경색이고, 투명한 자리에는 아무것도 그리지 않는다. 모드 뷰·덮개·안내표 버튼은 자판 폭 W 안이라 그대로다. **입력기 창 자체가 그 자리를 칠하지 않아야**(창 배경 투명) 아래 앱이 보인다 — 플랫폼 기본값과 이 앱의 창 설정은 LLD에서 확인한다(미확인, 10장 R11).
    - **터치 영역:** `KeyboardService.onComputeInsets`가 `touchableInsets = TOUCHABLE_INSETS_REGION`, `touchableRegion` = **자판 판**(창 좌표: 입력 뷰 좌표의 사각형 + 입력 뷰의 창 안 위치)으로 알린다(0.75까지 `TOUCHABLE_INSETS_VISIBLE` = 입력 뷰 전체). 영역 밖에서 시작한 터치는 플랫폼이 아래 창(앱)으로 보낸다. **`contentTopInsets`·`visibleTopInsets`는 바꾸지 않는다**(입력 뷰 위 끝 — 앱 화면이 밀리는 양은 0.75와 같다, SRS FR-CMN-14 ⑫ 사). 꽉 채움에서는 자판 판 = 입력 뷰 전체라 터치를 받는 자리가 0.75와 같다(그때도 같은 길로 사각형을 알릴지, `TOUCHABLE_INSETS_VISIBLE`을 쓸지는 LLD — 받는 자리가 같아야 한다). 입력 뷰가 아직 창에 붙지 않았거나 놓이기 전이면 0.75처럼 플랫폼 기본값을 둔다.
    - **갱신:** 자판 판은 루트가 놓일 때(`onLayout`) 정해지고, 플랫폼은 창을 다시 놓을 때마다 `onComputeInsets`를 다시 부른다(LLD에서 확인). 그래서 화면 방향·폭·정렬 설정·시스템 막대 여백이 바뀌어 루트가 다시 놓이면("다시 놓기") 칠하는 자리와 터치 영역이 같은 배치에서 함께 새 값이 된다. 모드 전환·덮개 여닫기는 x·R을 바꾸지 않아 자판 판이 그대로다.
    - **터치 길:** 자판 판 안의 자식 밖 자리(여유 칸, 빈 띠, 아래 여백, 닿은 쪽 옆 여백)는 0.75처럼 루트가 소비한다(입력·피드백 없음). 투명한 자리에서 시작한 터치는 보통 창에 오지 않는다. 다만 다른 손가락이 자판을 누르고 있는 동안 투명한 자리에 닿은 손가락을 플랫폼이 이 창으로 보낼 수 있으므로(미확인, R11), 루트의 **"자식 밖에서 시작한 포인터는 자식에 넘기지 않는다"(`OffKeyboardPointers`)는 그대로 둔다** — 창에 오더라도 입력이 없다(SRS FR-CMN-14 ⑫ 바). 자판 판에서 시작한 터치는 손가락이 터치 영역 밖(투명한 자리)으로 나가도 그 창이 끝까지 받을 것으로 본다(터치 영역은 누를 때의 창 선택에 쓰이는 것으로 봄 — 창 위로 나간 획을 받는 것과 같은 성질, 10장 R2. **실기 미확인, R11 ⑦**). 테두리(FR-SWP-45)는 그대로 자판 사각형의 바깥 변이다.
  - **띄운 자판(SRS FR-CMN-15, 오너 요청 2026-11-13, FSS#86):** 띄우기가 켜진 방향에서 자판 판을 입력 뷰 안에서 옮긴다. 0.76의 "칠하는 자리 = 터치 영역 = 자판 판 사각형 하나"를 그대로 쓰고, 더하는 것은 넷이다 — 입력 뷰 높이, 자판 판의 자리(세로 포함)와 손잡이 띠, 인셋(앱을 밀지 않음), 길게 눌러 끌기와 저장. **띄우기가 꺼진 방향은 0.76의 길을 그대로 탄다**(아래 "띄우기 끔").
    - **방법:** 입력기 창을 그대로 쓰고 **입력 뷰를 키워** 그 안에서 자판 판을 옮긴다. 딸린 창이나 다른 앱 위에 그리는 창을 쓰지 않고, 권한이 필요 없으며, 지금 뷰 구조(루트 하나에 모드 뷰)와 0.76의 장치(자판 판만 칠함, `touchableRegion`)를 그대로 쓴다. 띄운 자판이면 루트는 자기 높이를 "키 영역 6줄 + 아래 여백"이 아니라 **부모가 허용하는 가장 큰 높이**로 잰다. 플랫폼의 입력기 창은 내용 높이를 따라 커지는 것으로 보이나(공식 참조 문서의 입력 뷰·창 설명), **어디까지 커지는지(상태 막대·컷아웃 아래까지인지), 루트가 어떤 재기 조건을 받는지, 그때 위쪽 인셋을 받는지는 미확인**이다 — LLD가 공식 문서 근거를 적고, 못 대면 미확인으로 남긴다(10장 R12 ③).
    - **자리 계산(순수 함수, 안드로이드 없음, 단위 시험. 이름과 둘 자리는 LLD — 자판 판 계산 곁):** 입력 = 입력 뷰의 폭·높이, 네 변의 자리(왼쪽 l·오른쪽 r·아래 b = 0.76의 시스템 막대 여백과 같은 값, 위 t = 입력 뷰가 받은 상태 막대 인셋과 화면 컷아웃 인셋 가운데 큰 값 — 받은 것이 없으면 0. 옆·아래의 컷아웃은 따로 빼지 않는다 — 붙은 자판과 같은 취급, SRS TBD-33 ⑰, 실기 확인 R12 ③), `KeyboardWidth`가 낸 x·R, 자판 판 높이 P_h(= 손잡이 띠 높이 + 키 영역 높이), 그 방향의 띄우기 값, 저장된 fx·fy(각각 없을 수 있음)(모두 px). 출력 = **띄운 자판으로 놓는지**(띄우기 켬이고 S의 높이 ≥ P_h일 때만 참), **이동 영역 S**(입력 뷰 좌표: 왼쪽 l, 위 t, 오른쪽 폭 − r, 아래 높이 − b. S의 폭 = 가용 폭 A), **범위** X = A − R·Y = S의 높이 − P_h, **자판 판 사각형**(입력 뷰 좌표: 왼쪽 = l + fx × X, 위 = t + fy × Y, 폭 R, 높이 P_h). fx·fy는 0~1로 자른 뒤 쓴다. **저장된 fy가 없으면 fy = 1**(아래 끝), **저장된 fx가 없으면 가로 자리는 `KeyboardWidth`의 x를 그대로 쓴다**(왼쪽 = l + x — 정렬 설정의 자리이고 반올림까지 붙은 자판과 같다. 비율로는 왼손모드 0·중앙모드 0.5·오른손모드 1). 반올림은 LLD가 정하되 자판 판 전체가 S 안이어야 한다. 짝 함수 둘: **끌기** — (옮기기 시작 때의 자판 판 자리, 손가락 변위, S, R, P_h) → 가로·세로 따로 S 안으로 자른 자리(범위 0인 축은 그대로). **비율 내기** — (자판 판 자리, S, X, Y) → fx = (왼쪽 − l) / X, fy = (위 − t) / Y, **범위가 0인 축은 값 없음**(저장하지 않는다는 뜻). 놓을 때 시작 때의 자리와 견주어 **달라지지 않은 축을 저장에서 빼는 것**은 이 함수가 아니라 옮기기 상태 기계의 "놓기"(아래 ⓘ)가 한다(SRS FR-CMN-15 ⑨). 참이 아니면("붙은 자판") 이 함수는 자리를 내지 않고 0.76의 자판 판 계산을 그대로 쓴다.
    - **입력 뷰 높이와 놓기:** 루트가 잴 때 위 함수로 띄운 자판인지 정한다(부모가 허용하는 가장 큰 높이에서 t·b를 뺀 값이 P_h보다 작으면 붙은 자판으로 잰다). **이 판정은 같은 화면·같은 설정에서 하나로 정해져야 한다**(SRS FR-CMN-15 ④): 붙은 자판으로 놓인 낮은 입력 뷰는 위쪽 인셋을 받지 못해 t = 0으로 보일 수 있으므로, t를 어느 상태에서 어떻게 얻는지와 경계 높이 근처에서 붙은 자판 ↔ 띄운 자판이 되풀이되지 않게 하는 방법을 LLD가 정한다(미확인, R12 ③). 띄운 자판이면 모드 뷰·안내표 덮개·안내표 버튼을 0.76과 **같은 크기**(폭 W, 키 영역 높이 안의 같은 자리)로 재고, **자판 판 기준**으로 놓는다: 손잡이 띠 = 자판 판의 위쪽 R × 손잡이 띠 높이, 키 영역(자판 사각형)의 위 = 자판 판 위 + 손잡이 띠 높이, 모드 뷰의 왼쪽 = 자판 판 왼쪽 + m. 키 영역 안의 놓기(낮은 자판의 바닥 정렬, 빈 띠 버튼 = 자판 오른쪽 끝)는 0.76과 같다. 붙은 자판의 놓기 식("옆 여백 + x + m", 입력 뷰 바닥 정렬)은 고치지 않는다.
    - **칠하기·터치 영역·인셋:** 루트는 0.76처럼 **자판 판만** 키보드 배경색으로 칠하고(띄운 자판의 자판 판에는 아래·옆 시스템 막대 여백이 들지 않는다), `KeyboardService.onComputeInsets`는 `touchableRegion` = 자판 판(창 좌표)으로 알린다 — 같은 사각형 값 하나를 쓰는 것은 그대로다. **띄운 자판일 때만** `contentTopInsets` = `visibleTopInsets` = **입력 뷰의 높이(창 아래 끝)**로 알린다. 공식 참조 문서는 두 값을 "입력기 창 위 끝 기준"의 값이고 뒤의 앱을 크기 조절·밀기 하는 데 쓰인다고 적으므로, 창 아래 끝으로 주면 앱이 내줄 자리가 없다(SRS FR-CMN-15 ⑫). **실제로 앱이 밀리지 않는지와 앱이 키보드 보임을 어떻게 받는지는 미확인**이다(R12 ①). 붙은 자판일 때는 0.76 그대로다(위 끝 = 입력 뷰 위 끝).
    - **손잡이 띠:** 루트의 **자식 뷰 하나**로 둔다(이름 LLD). 키보드 배경색 위에 손잡이 표시 하나를 그리고(보통·잡힌 모양), 접근성 이름을 붙인다(문구 LLD). 붙은 자판에서는 없다(자리를 차지하지 않음). 자식으로 두는 까닭: 안드로이드 뷰 그룹은 첫 손가락을 받은 자식이 없으면 뒤에 닿은 손가락을 자식에게 나눠 보내지 않는 것으로 알고 있다(LLD에서 확인) — 띠가 여유 칸처럼 루트의 빈 자리면, 띠를 누른 채 키에 닿은 손가락이 모드 뷰로 가지 않아 SRS FR-CMN-15 ⑦ 마("뒤에 닿은 손가락은 보통의 자판 터치")를 지킬 수 없다. 띠는 키가 아니므로 `Feedback`의 키 입력 진동·소리를 부르지 않는다.
    - **옮기기 상태(순수 상태 기계 — 시각·좌표·기준값을 값으로 받음, 안드로이드 없음, 단위 시험. 이름 LLD):** 상태 = **쉼** / **기다림**(잡는 포인터, 누른 점, 누른 시각) / **끄는 중**(잡는 포인터, 시작 때의 자판 판 자리, 시작 때의 손가락 위치) / **버림**(그 포인터를 뗄 때까지). 사건과 옮김: ⓐ 쉼 + 창의 첫 손가락(`ACTION_DOWN`)이 손잡이 띠 안 → 기다림. ⓑ **쉼 또는 끄는 중**에, 다른 손가락이 닿아 있는 동안 손잡이 띠에 닿은 손가락(`ACTION_POINTER_DOWN`) → 상태 그대로, 그 포인터는 아무 일 없음(기다림 중에 닿은 손가락은 손잡이 띠에 닿았더라도 ⓔ를 따른다). ⓒ 기다림 + 잡는 포인터가 누른 점에서 가로 또는 세로로 잡기 허용 거리(8dp) 이상 → 버림. ⓓ 기다림 + 잡는 포인터 올라옴 → 쉼. ⓔ 기다림 + 다른 손가락 내려옴(어디에 닿든) → 버림(그 손가락은 보통 길로 간다: 키에 닿았으면 모드 뷰가 받고, 손잡이 띠·여유 칸·빈 띠에 닿았으면 아무 일 없음). ⓕ 기다림 + 누른 시각부터 길게 누름 시간 이상 지남 → 끄는 중, "옮기기 시작"(진동 한 번 — `Feedback`의 진동 설정을 따름, 손잡이 표시 바꿈). ⓖ 끄는 중 + 잡는 포인터 이동 → 자판 판 자리 = 끌기 함수(위). ⓗ 끄는 중 + 다른 손가락 내려옴 → 상태 그대로, 그 포인터는 뗄 때까지 입력 없음. ⓘ 끄는 중 + 잡는 포인터 올라옴 → "놓기"(비율 내기 → **자리가 시작 때와 px로 달라진 축만** 저장. 둘 다 같으면 저장 없음 — SRS ⑨), 쉼. ⓙ 끄는 중 + 취소(`ACTION_CANCEL`, 화면 방향 바뀜, 키보드 내려감, 다시 놓기) → "취소"(시작 때의 자리로 되돌림, 저장 없음), 쉼. 기다림·버림 + 같은 사건 → 쉼. ⓚ 버림 + 그 포인터 올라옴 → 쉼. **시간:** 길게 누름 시간은 `ViewConfiguration.getLongPressTimeout()`(⌫ 반복 첫 지연이 쓰는 값)이고, 기다림에 들어갈 때 반복 타이머와 같은 방식의 지연 호출 하나를 걸어 ⓕ를 넣는다(기다림을 떠나면 끈다). 시험은 시각을 값으로 넣는다. **좌표:** 손가락 위치는 루트(입력 뷰) 좌표로 본다 — 끄는 동안 루트는 움직이지 않고 자식만 움직이므로 변위가 SRS의 "화면 기준 위치"의 변위와 같다(움직이는 자식의 좌표로 재면 자판이 떨린다).
    - **터치 길:** 루트는 터치를 자식에게 나눠 주기 **전에** 위 상태 기계에 사건을 알린다. **끄는 중**에는 루트가 모든 포인터를 가로채 자식에게 넘기지 않는다(SRS ⑧ — 자판 입력 없음). 끄는 중에 새로 닿은 포인터는 옮기기가 끝난 뒤에도 뗄 때까지 자식에게 넘기지 않는다(`OffKeyboardPointers`와 같은 방식: 내려옴을 보내지 않으면 나뉜 이동·올라옴도 가지 않음). 손잡이 띠는 자식이지만 "자식 밖에서 시작한 포인터"와 **같은 취급**을 받는다: 다른 손가락이 모드 뷰를 누르는 동안 띠에 닿은 포인터는 모드 뷰로 넘어가지 않고 아무 일도 하지 않는다(ⓑ). `OffKeyboardPointers` 자체(여유 칸·빈 띠·자판 판 밖에서 시작한 포인터를 자식에 넘기지 않음)는 그대로 둔다. **모드 뷰는 고치지 않는다:** 받는 폭 W·키 기하·테두리(왼쪽 −m, 오른쪽 W + m, 위 0, 아래 높이)가 0.76과 같고, 손잡이 띠는 모드 뷰 밖이라 맨 윗줄에서 위로 나간 획은 0.76처럼 음수 y 좌표로 이동을 계속 받는다(R2와 같은 성질 — 0.76에서는 창 밖, 띄운 자판에서는 창 안의 형제 뷰 위).
    - **끄는 동안의 그리기와 갱신:** 끄는 동안에는 다시 재지 않고 자판 판의 자리 값만 바꿔 자식들과 칠하는 자리를 옮긴다(방법은 LLD — NFR-01의 프레임 예산 안이어야 한다). **터치 영역은 놓을 때와 취소할 때 반드시 새 자판 판으로 다시 알린다.** 끄는 동안에도 알릴지와, 창을 다시 놓지 않고 `onComputeInsets`가 다시 불리게 하는 방법은 LLD에서 확인한다(SRS ⑧).
    - **저장(7.3):** 방향마다 띄우기(참·거짓, 기본 거짓), fx, fy(0~1의 실수, 각각 없을 수 있음) — 키 여섯 개를 `SettingsStore`에 더한다. 자판 폭·정렬과 같은 흐름(Flow)으로 서비스·루트에 전달한다. 자리는 **놓을 때 한 번** 쓴다(끄는 동안에는 쓰지 않는다). 자기가 쓴 값이 흐름으로 돌아와 다시 놓기가 일어나도 자리가 같아야 한다(반올림 왕복 — LLD).
    - **다시 놓기:** 화면 방향(`onConfigurationChanged`, 8장), 설정 흐름(띄우기·키 크기·정렬·줄 높이), 인셋·입력 뷰 크기가 바뀌면 루트가 다시 재고 놓는다. 그러면 자판 판·터치 영역·인셋이 같은 배치에서 함께 새 값이 된다(0.76의 "갱신"과 같은 길). 붙은 자판 ↔ 띄운 자판이 바뀌면 입력 뷰 높이가 바뀌므로 창이 다시 놓인다. 옮기기·기다림 중이면 먼저 취소한다(상태 기계 ⓙ). 모드 전환·덮개 여닫기는 자판 판을 바꾸지 않는다.
    - **띄우기 끔(기본):** 루트와 서비스는 0.76의 길을 그대로 탄다 — 입력 뷰 높이, 놓기, 자판 판 계산, 칠하기, 터치 영역, 인셋이 같다. 손잡이 띠 뷰가 없고 상태 기계는 쉼을 떠나지 않는다. S가 낮아 붙은 자판으로 놓이는 방향도 같다. 이것을 시험으로 고정한다(11장).
  - **입력 연습:** 연습 화면(`PracticeActivity`, 7.1)의 자판 틀도 같은 함수로 자판 사각형·여유 칸·자판 자리를 정하고 같은 방식으로 놓는다(자판 뷰는 폭 W, 양쪽에 여유 칸, 테두리의 왼쪽·오른쪽 = 자판 사각형의 바깥 변). 가용 폭 = 그 화면의 자판 자리 폭, 방향 = 연습 화면의 구성. 여유 칸은 자판 뷰 밖의 키보드 배경색 자리이고 터치를 소비한다(입력 없음). **남는 자리는 칠하지 않는다(0.76, FSS#85, SRS FR-CMN-14 ⑫ 자):** 자판 틀은 틀 전체 배경을 두지 않고 자판 사각형만 키보드 배경색으로 칠해(틀에는 시스템 막대 여백이 없어 자판 판 = 자판 사각형) 남는 자리에 연습 화면의 배경이 보인다. 아래에 다른 앱이 없어 터치 영역을 줄이는 일은 없다: 남는 자리의 터치는 자판 뷰에 넘기지 않아 입력이 없다(틀이 소비하든 연습 화면으로 넘기든 LLD — 연습 화면은 그 자리에 누를 것을 두지 않는다). **띄우기는 적용하지 않는다(SRS FR-CMN-15 ⑭, FSS#86):** 자판 틀은 띄우기 값을 읽지 않고 손잡이 띠 뷰를 두지 않는다.
  - **설정 화면(SRS FR-SET-09):** 키 크기 슬라이더의 위 끝은 그 방향의 대략의 가용 폭 / 11을 올림한 칸이고(0.74까지 / 10), 미리보기의 전체 폭은 자판 사각형 폭(11 × 키 크기, 꽉 채움이면 가용 폭)이다. 같은 `KeyboardWidth`의 상수·함수에서 얻는다. **띄우기(FSS#86):** 방향 상자마다 키 크기·정렬 아래에 "띄우기" 스위치(기본 끔)와 안내 한 줄을 둔다. 정렬은 띄우기와 상관없이 고를 수 있다(꽉 채움이면 흐린 것은 그대로).
- **글자 키 획:** `stroke-core`로 ↑·↓·문지르기를 판정해 탭 자판 동작 표(SRS 3.3)대로 입력한다. 나갔다 돌아옴과 ←·→ 문지르기는 그 방향 나감으로 본다(DCR-02). 시프트 상태는 없다(↑ 나감이 유일한 시프트).
- **처리 시점(SRS FR-CMN-11a, DCR-11):** 기능키는 누를 때, 키 입력 진동·소리도 누를 때. 모드 키만 뗄 때 결과를 정한다(8.2절, 이슈 #205). `ACTION_CANCEL`이면 아직 떼지 않은 모든 포인터가 결과 없이 대기열에서 빠지고 반복은 멈춘다. 이미 뗀 포인터의 대기 결과는 누른 순서대로 낸다.
- **여러 손가락(FR-CMN-11):** 포인터마다 따로 추적한다. 글자·숫자·기호 키는 결과를 각 포인터를 뗄 때 정하고, 출력은 누른 순서로 낸다. 먼저 누른 글자·숫자·기호 키가 아직 눌려 있으면 뒤 포인터의 결과를 대기열에 두었다가 앞 결과가 나온 뒤에 낸다. 기능키(⌫, 스페이스, ↵, ⇥, 방향키)는 누르는 즉시 처리하고 대기열에 들어가지 않으며, 다른 키를 기다리게 하지도 않는다. 모드 키는 뗄 때 결과를 정하므로 글자·숫자·기호 키처럼 대기열 순서에 든다(SRS FR-CMN-11, 이슈 #205).
- **탭 키:** 조합 확정 → `commitText("\t")`.
- **방향키:** 조합 확정(`finishComposingText`) → `sendKeyEvent(KEYCODE_DPAD_LEFT/RIGHT/UP/DOWN)`. 누르고 있으면 반복(첫 지연 후 일정 간격).
- **⌫:** 누르고 있으면 반복(방향키와 같은 타이머, FR-CMN-07c).
- **접근성(NFR-07):** 커스텀 Canvas 뷰에 `ExploreByTouchHelper`로 키마다 가상 접근성 노드를 제공한다(쿼티·두벌식).
- 한자 변환은 범위에서 뺐다(SRS 1.2절).

안내 팝업(방향 안내·획 안내·현재 글자·다음 글자), 획 자국, 가운데 글자는 긋기 자판에만 있던 표시라 긋기 입력 모드와 함께 없앴다(SRS 3.5). 표시 지연 타이머, 세 안내 설정, 획 자국 설정도 없다. 탭 자판의 키 변 글자 표시는 5A, 그래피티의 인식 글자 표시와 획 안내표는 5장이다.

## 7. 입력 연습과 저장소

### 7.1 입력 연습 (옛 튜터 모드, FSS#17)

오너 방향(2026-11-02, FSS#17)에 따라 영문 대문자·기호·그래피티를 **주제별로 골라서 짧게** 연습한다. 아무것도 재지 않는다(기준값 고정, SRS 1.3). 규칙의 정본은 SRS 부록 A다(A.1 화면, A.2 주제·항목, A.3 판정. 0.78까지는 긋기 입력 규칙 문서 10장). 코드 이름은 `PracticeActivity`·`PracticeItemJudge`로 바꾼다(옛 `TutorActivity`·`TutorItemJudge`). 요구사항 ID(SRS FR-TUT)는 그대로 둔다.

```
PracticeActivity(옛 TutorActivity)
  └─ 주제 목록 = ①②③-1③-2 (SRS 부록 A.2)
       │     주제마다 이름·한 줄 설명·어림 시간·해 본 표시(✓, SettingsStore의 값, 판정에 안 씀. 지금 없는 주제의 값은 무시, SRS FR-CMN-10a ③)
       │     그래피티가 키보드에서 꺼져 있으면 ③-1·③-2에 "꺼져 있음" 표시(할 수는 있음, SRS FR-CMN-03f ⑦)
       ├─ 주제 설명(한 화면) → [시작]
       ├─ 항목을 정해진 순서로 한 번씩(되풀이·표본 없음). 다 맞히면 끝 화면 → 주제 목록. [그만]은 언제든 주제 목록으로
       ├─ 연습 자판 = 주제·항목이 정함(실제 키보드와 같은 뷰·엔진·고정 기준값):
       │     ①·② 탭 자판: 실제 탭 자판 그대로(TapKeyboardView 배치 데이터(영문 쿼티), 편집 줄·⌫ 포함) + stroke-core 탭 자판 동작 표(↑ 대문자·짝 기호, ←·→·↓ 배정)
       │     ③ 그래피티: GraffitiPadView + recognizer(5장) + GraffitiGuidePanel을 늘 펼친 상태로, 목표 칸이 보이게 넘겨서. 항목마다 패드의 한영 상태를 목표에 맞춤. 자음·쌍자음과 알파벳 전체를 한 번씩(FSS#72)
       ├─ 입력 표시: 마지막 한 글자 크게(SRS FR-TUT-09, 임시 ㆍ·‥ 그대로). 조합기는 실제와 같은 HangulComposer(4.4)
       ├─ PracticeItemJudge(옛 TutorItemJudge): 동작(터치 하나, 그래피티는 획 하나)마다 실제 판정 결과를 목표와 비교 → 다르면 ✗, 다 맞으면 ✓(SRS FR-TUT-12). 그래피티는 확정된 글자만(조합 중 글자는 판정 안 함, 다음 자음·스페이스로 확정, 마지막 글자는 스페이스, FSS#43)

첫 실행: SettingsActivity가 처음 한 번 주제 목록만 연다(연습은 시작하지 않음, SRS FR-TUT-01). 그 뒤는 설정의 "입력 연습"으로만

- **판정 입력:** `PracticeItemJudge`는 Android 의존 없는 순수 Kotlin으로 `app` 소스에 두고 JVM으로 시험한다. 입력인 동작 기록은 공통 타입이다(넣은 글자 또는 자모·천지인 요소, 무시·인식 실패 표시). 탭 자판 항목은 ⌫를 반영한 글자열로 판정한다(앞부분이 아니면 ✗, 항목을 비우지 않고 ⌫로 고쳐 이어 씀, 같아지면 ✓, SRS 부록 A.3). 이름·타입 세부, ✓·✗ 표시 시간, 화면 문구는 LLD.
- **빠지는 것(FSS#17):**
  - 1·3·5과 차례와 과 번호, 단계 목록(1-1·1-2·3-1·3-4·5-1) — 주제·항목 목록으로 바뀐다.
  - 번갈아 쓰기·되풀이·표본 수·짝 규칙, 위치 오차 기록(`calibration.position`).
  - 1-1·1-2 특별 판정과 "✓이면 목표 글자로 바꿈"(SRS TBD-17 해당 없음).
  - 5과 문장·`TypingStats`·5과 ⌫, 19자음 돌림(오너 결정 ③).
  - 기준값 저장 파일과 내보내기·가져오기·초기화 메뉴(오너 결정 ①, 7.2·7.3).
  - 그 전의 `ThresholdEstimator`·흔들림 여유·겹침 다시 하기, 시간 창 계수, 3-2·한 획 복모음 측정은 이미 없앴다.
- 최소 통과 거리는 **dp 절댓값**이다. 가로 화면이나 줄 높이 설정(FR-SET-06)·자판 폭 설정(FR-SET-09)으로 키 크기가 달라져도 비율로 바꾸지 않는다(SRS FR-CMN-12).
- `minCrossDp` 하나를 탭 자판·모드 키·그래피티 보조 줄 모드 키가 함께 쓴다(키 변 너머 거리, 4.2). **값은 8dp 고정**이다(오너 결정 2026-11-02, SRS TBD-29 확정). 0.50까지의 기본값은 14dp였다.
  - **영향(설계자 확인):** 탭 자판 ↑·↓의 나감·들어옴은 변 너머 8dp다(`EdgeCrossingTracker`가 같은 값을 받음). 이 문턱은 누른 점이 아니라 **키 변에서** 잰다. 그래서 키 가운데를 누른 탭은 반 키(약 25dp) + 8dp를 움직여야 나감이 되고, 안드로이드 touch slop(누른 점에서 8dp)보다 둔하다. 나갔다 돌아옴(같은 변 2번)·문지르기(3번 이상)는 변 안팎을 8dp씩 오가야 해 흔들림으로 생기기 어렵다.

### 7.4 내 획 학습 (SRS FR-TUT-14~17, FSS#96)

세부는 PM 권장안이고 오너 확인 전이다(SRS TBD-30). 7.1의 "재는 것·저장하는 것 없음"은 연습 주제의 것이고, 획을 저장하는 곳은 이 주제뿐이다.

```
PracticeActivity
  └─ 주제 목록: 연습 주제들 아래 "내 획 학습"(✓ 대신 개인 획이 있는 글자 수)
       └─ 글자 목록: 한글 자음 14, 영문 25(i 제외). 글자마다 저장된 획 수(0~8). [전체 초기화](한 번 물음)
            └─ 글자 쓰기 화면: 목표 글자, 그 글자의 안내표 칸, GraffitiPadView, [다시 학습] [초기화]
                 손을 뗌 → InkStroke
                   ├─ 숫자 영역에서 시작했거나 StrokeRules가 규칙 획으로 판정 → 저장하지 않고 까닭을 알림
                   └─ 그 밖 → ① 저장하기 전 구성으로 인식한 결과를 보임(그 글자의 기본 집합, 대기 없음)
                              ② 저장소에 그 글자의 획으로 더함(8획이 차 있으면 가장 오래된 획을 뺌)
                              ③ 새 개인 획 목록을 인식기에 넘김(5.1)  ④ 획 수를 고쳐 보임
```

- **개인 획 저장소(`app`, 이름과 파일 형식은 LLD-07):** 읽기(전체), 더하기(글자, 획), 글자 하나 지우기, 모두 지우기. 8획 한도와 "가장 오래된 획 빼기"는 안드로이드 의존 없는 순수 Kotlin으로 두어 JVM으로 시험한다. 쓰다가 멈춰도 앞의 파일이 깨지지 않게 쓰는 방법과 읽을 수 없는 파일의 처리는 LLD-07이 정한다. 읽지 못하면 빈 목록이다(SRS FR-TUT-15 ④).
- **저장할지 가르는 판정**(규칙 획·숫자 영역 획은 저장하지 않음, 대상 글자 목록)도 순수 Kotlin으로 두고 JVM으로 시험한다. 규칙 획 판정은 `recognizer`의 `StrokeRules`를 그대로 쓴다(인식과 같은 기준).
- 이 화면은 `GraffitiState`, 조합기, `CheonjiinAssembler`, `PracticeItemJudge`를 쓰지 않는다(획이 글자로 입력되지 않고 ✓·✗ 판정도 없다).
- **다시 학습 = 글자 지우기 + 쓰기 화면, 초기화 = 글자 지우기, 전체 초기화 = 모두 지우기.** 지운 뒤에도 새 목록을 인식기에 넘긴다. 내장 템플릿과 출고 예시는 저장소에 없으므로 지워지지 않는다.
- **실제 입력 경로는 저장소에 쓰지 않는다:** 저장소의 쓰기 함수를 부르는 곳은 학습 화면뿐이다(`KeyboardService`·`GraffitiPadView`의 입력 경로와 연습 주제는 읽기만 한다, SRS FR-TUT-17 ①). 검사와 시험으로 지킨다(11.1).
- **키보드 반영:** 5.1 "서비스 연결".

### 8.1 ModeController: 모드 키 규칙

```
상태: current, previous(없을 수 있음), typed
순서: DUBEOLSIK → QWERTY → GRAFFITI → DUBEOLSIK … (오너 결정 2026-11-14, FSS#95. 설정에서 꺼진 모드는 건너뜀, FR-CMN-03f)
켜진 모드: enabled ⊇ {QWERTY, DUBEOLSIK}(늘 켜짐), GRAFFITI는 SettingsStore 값(기본 켬, FR-SET-08)
nextEnabled(m) = 순서상 m 다음의 첫 켜진 모드

입력 이벤트(글자·숫자·기호, 그래피티 천지인 요소 획, 스페이스, 엔터, 탭, 지우기) → typed = true
  (방향키, 모드 키, 그래피티 한영 전환·시프트·캡스록·확장 시프트·'J' 확정 획 → 입력 아님, DCR-17)
입력창 바뀜(onStartInputView) → typed = false, previous 유지          // FR-CMN-03e
  숫자류 입력창이면 enterNumericField():                                 // FR-CMN-04, 04b
    if returnMode == null: returnMode = current
    current = QWERTY                       (previous·마지막 모드 저장 안 바꿈)
  아니면 leaveNumericField():
    if returnMode != null: current = returnMode; returnMode = null   (previous 안 바꿈)
applyEnabled(enabled)  — 설정이 바뀌었을 때(키보드가 화면에 보이고 있으면 곧바로)와 onStartInputView마다    // FR-CMN-03f ②~④
  if previous ∉ enabled: previous = null
  if returnMode != null and returnMode ∉ enabled: returnMode = nextEnabled(returnMode); 마지막 모드 저장(= returnMode)
  if current ∉ enabled: 확정(FR-CMN-03d); current = nextEnabled(current)   (typed·previous 안 바꿈)
                        if returnMode == null: 마지막 모드 저장
프로세스 시작 → current = 저장된 마지막 모드(저장이 없으면 순서의 첫 모드 DUBEOLSIK. 저장된 이름이 지금 없는 모드(옛 긋기 입력)면 없는 것으로 읽음, FR-CMN-10a. 꺼져 있으면 nextEnabled로 고치고 마지막 모드로 저장), previous = 없음, typed = false, returnMode = 없음
모드 키 →
  확정(finishComposingText, 입력 단위 목록은 확정으로 소멸. 그래피티의 성립 전 천지인 임시 글자는 버림)   // FR-CMN-03d
  if typed and previous != null and previous != current:  next = previous      (previous는 늘 켜진 모드, applyEnabled)
  else:                                                    next = nextEnabled(current)
  if typed: previous = current
  current = next; typed = false
  if returnMode == null: 마지막 모드 저장(DataStore)   // 숫자류 입력창 안에서 바꾼 모드는 저장 안 함, FR-CMN-04b
```

- 순수 Kotlin 상태 기계로 만들어 SRS 모드 키 예시 표 10행, 숫자류 입력창 사례 표 7행, 꺼진 모드 사례 표 6행(FR-CMN-03f)을 단위 시험한다. 켜진 모드 집합은 밖(`SettingsStore`)에서 받아 넣는다.
- **설정 변경 전달:** `KeyboardService`가 `SettingsStore`의 켜진 모드 값(Flow)을 구독한다. 값이 바뀌면 `applyEnabled`를 부르고, 입력 뷰가 화면에 보이는 동안 `current`가 바뀌었으면 입력 뷰를 새 모드의 뷰로 바꾼다(`setInputView`, 모드 전환과 같은 경로). 화면에 보이고 있지 않으면 다음 `onStartInputView`의 `applyEnabled`가 맡는다.
- 그래피티 안의 한영 상태(`GraffitiState`, 5장)는 `ModeController`와 따로이고 켜진 모드와 상관없다(FR-CMN-03f ⑥).
- 숫자류 입력창 안에서도 모드 키는 위 규칙 그대로다(typed·previous 포함). 마지막 모드 저장만 하지 않으므로, 숫자류 입력창 안에서 프로세스가 다시 시작되면 저장된 마지막 모드(= 돌아갈 모드)를 `returnMode`로 삼아 다시 쿼티로 시작한다(사례 표 7행).
- 위 "모드 키 →"는 모드 키의 **탭** 결과(8.2절의 `ModeKeyTap`)일 때만이다. ↑(설정 열기)는 `ModeController`를 거치지 않는다.

### 8.2 모드 키 획: 탭 = 모드 전환, ↑ = 설정 (SRS FR-CMN-13, 오너 결정 2026-11-02, 이슈 #205)

- **공용 판정 `ModeKeyGesture`:** 두 입력 뷰(탭 자판, 그래피티 보조 줄)의 모드 키가 같은 판정을 쓴다. 누를 때 키 입력 진동·소리만 내고(FR-CMN-11a ②), 포인터를 따라가며 `stroke-core`의 변 통과 기록(최소 통과 거리. 테두리에 붙은 변은 닿으면 나감 — SRS FR-SWP-03·45)에서 **처음 통과한 변**을 본다. 손을 뗄 때 첫 변이 위면 `OpenSettings`, 아니면(통과 없음, ←, →) `ModeKeyTap`이다. 되돌아옴·문지르기·꺾기·길이는 보지 않는다. `ACTION_CANCEL`이면 결과가 없다(SRS FR-CMN-11a ③).
- **`ModeKeyTap`** → 8.1 모드 키 규칙 그대로.
- **`OpenSettings`** → 조합 확정(`finishComposingText`, 방향키·Esc와 같음) → 설정 화면(`SettingsActivity`) 시작. `ModeController`의 current·previous·typed·returnMode와 마지막 모드 저장은 바꾸지 않는다(SRS FR-CMN-03a: 모드 키는 입력 아님). 입력기 서비스에서 액티비티를 여는 방법(플래그 등)은 LLD에서 정한다.
- **처음 누른 키로만 판정:** 손가락이 위 줄 키·빈칸·그래피티 패드로 넘어가도 그쪽은 입력이 없다. 그래피티에서는 모드 키에서 시작한 포인터를 인식기(`InkCollector`)에 넣지 않는다.
- **여러 손가락:** 탭 자판은 글자 키와 같은 대기열 순서(SRS FR-CMN-11). 그래피티 패드는 한 획 진행 중 다른 손가락을 무시하는 지금 규칙 그대로다.
- **그래피티 획 안내표 덮개**가 열린 동안은 모드 키가 덮개 아래라 터치가 닿지 않는다(5장, SRS FR-GRF-09a).
- **단위 시험(JVM):** 변 통과 기록 → 결과: 탭(이동 없음·최소 통과 거리 미만), ↑, ←, →, ↑ 뒤 되돌아옴(= ↑), → 뒤 위로 꺾음(= 탭), 테두리 변(↓)에 닿음(= 그 방향 나감, 모드 키는 탭과 같음, 이슈 #237), 여유 칸 쪽 ←(보통 변 통과, 모드 키는 탭과 같음, FSS#84). `OpenSettings` 뒤 `ModeController` 상태 불변.

## 9. 오류 처리

- 엔진 호출(변 통과 판정, `recognize`, 조합기 이벤트)을 획 단위로 감싼다. 예외가 나면 그 획은 결과 없이 버리고, 조합 상태는 획 시작 전으로 되돌린다(입력 단위 목록 이용, 4.4). 오류는 7.3의 규칙대로 기록한다(NFR-03, NFR-05).
- 기준값 파일이 없거나 손상되면 기본값으로 동작한다(FR-TUT-05). 따로 안내하지 않는다.
- `InputConnection`이 없으면(null) 아무것도 쓰지 않는다.
