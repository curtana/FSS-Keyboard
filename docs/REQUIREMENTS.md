# 사용자 요구사항과 구현 가능성 분석

- 버전: **0.33** (2026-11-14)
- 상태: 초안. 설계 문서에서 요구사항을 뽑아 구현 가능성을 분석했다.
- 근거 문서:
  - 긋기 입력 규칙 문서(0.4 기준으로 처음 도출). **긋기 입력 모드를 삭제하면서(오너 결정 2026-11-14, FSS#95) 그 문서도 지웠다.** 긋기 입력 모드의 요구(UR-B1~B9, B14~B18, B22, B24, B25)는 삭제 표시로 남기고 번호는 다시 쓰지 않는다. 남는 동작(탭 자판·모드 키의 방향 긋기, 입력 연습)의 규칙은 SRS 1.3·3.4·부록 A에 있다
  - 그래피티 규칙 문서(비공개, `docs-private/GRAFFITI_FEASIBILITY.md` — 저장소에 올리지 않음, 이슈 #249. 아래의 "GRAFFITI n.n"은 이 문서의 절) 0.5 (그래피티, 처음 도출 기준). UR-C6은 0.16 기준으로 더했다(오너 요청 2026-11-01, 이슈 #189: 획 안내표 팁)
  - UR-C2는 그래피티 규칙 문서 0.17 기준으로 고치고 UR-C7·C8은 더했다(오너 결정·방향 2026-11-05, FSS#64)
  - UR-C7은 영문 글자까지 넓혔다(오너 결정 2026-11-06, FSS#80)
  - UR-A10은 더했다(오너 요청 2026-11-13, FSS#84: 자판 좌우 여유 칸). UR-A9·UR-B11·NFR-2·R1을 그에 맞춰 고쳤다
  - UR-A11은 더했다(오너 요청 2026-11-13, FSS#85: 자판 옆 남는 자리를 투명하게, 터치는 아래 앱으로)
  - UR-A12는 더했다(오너 요청 2026-11-13, FSS#86: 자판을 띄워 길게 눌러 옮기기. 분석 `_workspace/analysis/floating-keyboard/report.md`)

## 1. 결론

**설계한 내용은 모두 구현 가능하다.** 판정 규칙은 순수 계산(터치 좌표, 시간, 키 사각형)이라 막히는 기술 요소가 없다. 다만 다음 두 가지는 **실기기 프로토타입으로 먼저 확인**해야 한다.

| 번호 | 확인할 것 | 왜 중요한가 |
|---|---|---|
| 1 | **화면 좌우 끝의 시스템 뒤로 가기 제스처**와 끝 키(탭 자판 1·q·0·p 등)의 방향 긋기 충돌 | 제스처 내비게이션을 쓰는 기기에서 끝 키를 안쪽으로 밀면 뒤로 가기가 먼저 동작할 수 있다 |
| 2 | 손가락이 **키보드 창 밖(위쪽 앱 화면)으로 나가도** 움직임이 계속 들어오는지 | 키에서 시작한 획이 창 밖으로 이어질 때의 판정이 여기에 의존한다 |
| 3 | ~~안내 표시를 키보드 위쪽까지 띄울 수 있는지~~ | 삭제(오너 결정 2026-11-14, FSS#95: 긋기 입력 모드 삭제). 안내 표시가 없어졌다 |

그 밖에 **설계에서 아직 정하지 않은 사용자 요구**가 있다(5장). 가장 중요한 것은 **입력 모드를 어떻게 전환하는지**다(G1, 해결됨).

## 2. 범위와 용어

- **대상:** 안드로이드 키보드 앱(IME) 하나. 입력 모드 3가지(한글 두벌식, 영문 쿼티, 그래피티)를 제공한다(오너 결정 2026-11-14, FSS#95: 긋기 입력 모드 삭제. 0.32까지 4가지).
- **사용자:** 오너 본인(우선). 공개 여부는 따로 결정.
- **용어:** 변 통과 용어(탭, 나감, 들어옴, 나갔다 돌아옴, 문지르기)와 "방향 긋기"는 SRS 1.3을 따른다.
- **판정 표기:** ✅ 가능 / ⚠️ 조건부(확인·결정 필요) / ❗ 위험(대책 필요)

## 3. 사용자 요구사항과 분석

### 3.1 공통

|---|---|---|---|---|
| UR-A1 | 세 입력 모드(한글 두벌식, 영문 쿼티, 그래피티)를 하나의 키보드 앱에서 쓸 수 있다(FSS#95, 0.32까지 긋기 입력을 넣어 넷). 모드 키 순환 순서는 한글 두벌식 → 영문 쿼티 → 그래피티다 | ✅ | `InputMethodService` 하나에서 입력 뷰를 바꿔 끼운다 | 모드 전환 = 한/영 키(5장 G1 해결, SRS FR-CMN-03). 긋기 입력 모드가 있던 버전에서 올려도 죽지 않고 한글 두벌식으로 시작한다(SRS FR-CMN-10a) |

| UR-A9 | 넓은 화면(태블릿 등)에서 키보드 폭을 줄여 왼쪽·가운데·오른쪽에 둔다(왼손모드·중앙모드·오른손모드). 폭·정렬은 세로·가로 화면을 따로 기억한다. 폭은 키 한 칸 크기로 정한다. 세로 기본 = 폭 꽉 채움, 가로 기본 = 세로와 같은 키 크기 + 가운데(오너 결정 2026-11-02, FSS#25) | ✅ | 키 한 칸 크기를 고르면 자판 폭 = 10칸 × 키 크기(하한 320dp)로 정해지고(양쪽 반 칸 여유를 넣은 11칸이 가용 폭에서 멈춤, UR-A10), 입력 뷰가 그 폭과 자리로 모드 뷰를 그 폭으로 재고, 남는 자리는 투명한 자리로 둔다(UR-A11, FSS#85. 0.30까지는 입력 없는 여백). 키 배치는 폭에 비례하므로 배치 데이터는 그대로(SRS FR-CMN-14, FR-SET-09) | 줄인 폭에서 키가 NFR-2보다 작아질 수 있음(사용자 선택이라 허용). |

| UR-A12 | 자판을 화면 아래에 붙이지 않고 띄워서, 길게 눌러 끌어 자리를 옮긴다. 태블릿 가로 화면에서 자판이 화면 절반을 가리는 것이 주된 이유다(오너 요청 2026-11-13, FSS#86: "키보드 부동형으로 만들어서 길게 눌러서 이동할 수 있도록 해줘", "태블릿에서극명하게드러나 가로모드면 화면 절반이안보여서 플로팅이 필요해") | ✅ | 공개 API만 쓰고 권한이 필요 없다. 입력기 창의 입력 뷰를 화면 높이 쪽으로 키우고 그 안에서 자판을 옮긴다. 자판(손잡이 띠 포함) 밖은 그리지 않고 터치를 받지 않으며(UR-A11과 같은 장치), 앱에는 자판이 차지하는 자리가 없다고 알려 앱 화면을 밀지 않는다. 설정의 세로·가로 상자에서 따로 켜고(기본 끔), 띄웠을 때만 자판 위에 생기는 손잡이 띠를 길게 눌러 끈다. 자리는 방향마다 따로 기억하고 시스템 막대·컷아웃을 뺀 영역 안에만 놓인다(SRS FR-CMN-15, FR-SET-09) | **실기 미확인**(앱에 자리 0을 알렸을 때의 반응, 화면만 한 투명 입력기 창의 부작용, 입력 뷰를 키울 수 있는 높이, 시스템의 키보드 내리기·전환 버튼, 둘째 손가락, 분할 화면 — 태블릿 가로 화면부터 확인, HLD 10장 R12). 앱 화면을 밀지 않으므로 입력창이 자판 밑에 깔릴 수 있고 그때는 사용자가 자판을 옮긴다. 꽉 채움(세로 화면 기본)이면 위아래로만 움직인다. 길게 누를 자리·범위·켜고 끄는 방법 등은 PM 권장안이고 오너 확인 전이다(SRS TBD-33). 끌어서 아래에 붙이기, 크기 조절, 스스로 비키기, 반투명은 이번에 하지 않는다 |

## 6. 권장 진행 순서

1. **판정 엔진 프로토타입**(`stroke-core`, 순수 Kotlin): 키 변 통과 판정을 구현하고 저장소 안 테스트 데이터와 단위 테스트로 고정한다. 기기 없이 JVM에서 검증된다.
2. **실기기 확인용 최소 키보드:** 자판 배치 + 터치 추적만 넣어 R1·R2를 확인한다.
3. **입력 연습 화면:** 주제별 연습 자판으로 실제 판정을 해 보며 실기기에서 오판정을 확인한다(재는 것 없음, FSS#17).
4. **조합 엔진**(`core-hangul`)과 두벌식·쿼티 자판.
5. **그래피티 인식기**와 필기 패드.
6. 5장 결정 사항은 1~2단계와 함께 정한다. 특히 **G1(모드 전환)**은 2단계 전에 정한다.
